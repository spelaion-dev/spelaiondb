SpelaionDB 0.15.0 takes the engines and plugins we already ship further: ClickHouse searches,
explains and imports; RisingWave, Materialize, CrateDB, StarRocks and Babelfish connect through
the plugins they speak; SQL Server LocalDB opens over its pipe on Windows. Where an engine cannot
keep a safeguard, the app says so and refuses, instead of pretending.

## ClickHouse
- **Data search**, with every value bound, as on the other engines.
- **Plans** in the plan view and for agents (`EXPLAIN json = 1, …`).
- **Imports that land whole or not at all.** ClickHouse has no transactions, so an import loads
  into a table of the app's own beside the target and puts it in place in one atomic step at the
  end (`RENAME` or `EXCHANGE TABLES`); a failure or a cancel drops that table and leaves the
  target untouched. Appending to an existing table, and databases that are not Atomic, are
  refused. Tables left behind by an app that quit mid-import are listed by the next import
  (ADR-066).

## More engines through the plugins
- **RisingWave** (PostgreSQL plugin): browse, query and edit. Agents and read-only connections
  stay refused: its read-only transaction lets functions that reach other databases and storage
  through, and a view can hide them.
- **Materialize** (PostgreSQL plugin): browse and query; agents, read-only connections and
  streaming reads stay refused, since its `BEGIN READ ONLY` lets `CREATE` and `DROP` through.
- **CrateDB** (PostgreSQL plugin): browse and query; its editor sessions follow no transaction.
- **StarRocks** (MySQL plugin): browse and query, primary keys included; imports and multi-
  statement edits are refused where its transactions cannot hold them.
- **Babelfish** (SQL Server plugin): transactions and keys hold, so imports and edits work; agents
  and read-only connections are refused. A running statement is cancelled from a second
  connection, since Babelfish answers SQL Server's cancel only when the statement ends.
- **SQL Server LocalDB** on Windows, through its named pipe, starting the instance if it is not
  running. Windows authentication is the default; a SQL login warns that its password crosses
  the local pipe without TLS.
- Engines that ignore transactions (CrateDB, RisingWave, GreptimeDB, StarRocks) always run in
  auto-commit: Commit and Rollback say they are not available instead of showing writes as held
  back that were already written.

## Fixes
- **Cancelling an import never interrupts its own `BEGIN`, `COMMIT` or `ROLLBACK`.** Before, a
  cancel at that moment could leave a SQL Server session answering every later request with
  error 3989; now the import rolls back right after.
- **Oracle stays without a read barrier, now with the evidence.** No session setting holds: a
  function can undo `DISABLE COMMIT IN PROCEDURE` or `READ_ONLY` with its own `ALTER SESSION` and
  write, through a database link too. Agents and read-only connections stay refused on Oracle.
- **Agents' writes are refused on servers whose writes are not atomic.**
- Result edit actions show at once, and catalog reads are not repeated.
- An AWS SSM-only tunnel says why it cannot run commands.

## Interface
- **Hide the side panel** from a button on its header or with Ctrl+B; the app remembers whether
  it was hidden and how wide it was.

## Under the hood
- ADR-065: one lexical scanner per SQL dialect, shared by the splitter, the placeholder scanner,
  the guard's fallback and the remote SQLite check (implementation in follow-up cards).
- The release builds the CLI once, inside each platform's app build.
- The plugins' CI keeps DuckDB's unpacked sources out of the Rust cache.
- SignPath Foundation declined to sign the Windows installers for now (the project is too young);
  they stay unsigned until it applies again.
- `cookie` 0.18.3, `parquet` and `arrow` 60.2.0 (RUSTSEC-2026-0594, RUSTSEC-2026-0595).
