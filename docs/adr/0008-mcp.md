# ADR-008: MCP server

- **Status:** Accepted
- **Date:** 2026-11-02

## Context
Agents must be able to explore schemas and query without being able to destroy production
or leak data by accident. Data returned by the database is untrusted content (possible
prompt injection).

## Decision
- **Transport:** stdio. (HTTP+SSE is deprecated in MCP; Streamable HTTP would only be
  needed for remote access.)
- **Identity:** there is no reliable agent identity; the model is **profiles**
  (`spelunk mcp --profile analyst`) that define visible connections and permissions.
- **Defense in layers:**
  1. No connection exposed by default (explicit `mcp.exposed = true`).
  2. Read-only database credentials specific to the MCP (the only real guarantee).
  3. Read-only transaction (`BEGIN READ ONLY` + `ROLLBACK` in PG,
     `START TRANSACTION READ ONLY` in MySQL, a read-only file in SQLite).
  4. Statement classifier in the core (`sqlparser-rs`); whatever does not parse is
     rejected. It must catch `EXPLAIN ANALYZE`, DML inside `WITH`, several statements
     (in PG, use the extended protocol) and `SET` that disables read-only mode.
  5. Limits: timeout, rows, bytes per response, truncation of long fields.
  6. *(Superseded by ADR-019: per-connection writes, production included, no confirmation for now.)*
     Writes (v0.3): a separate `execute_write` tool; per-connection policy
     `deny` (default) | `confirm` | `allow`; `env = "prod"` is always `deny` for the MCP;
     human confirmation in the app, running in a transaction and showing affected rows
     before the commit.
  7. Append-only audit log in the local SQLite.
- **Tools:** `list_connections`, `list_objects`, `describe_table`, `search_schema`,
  `run_query`, `explain_query` (+ `execute_write` in v0.3), with `readOnlyHint`/
  `destructiveHint` annotations.
- **SDK:** `rmcp` (official).

## v0.1 implementation (2026-11-02)
- `spelunk mcp` (crate `spelunk-mcp`, binary `apps/cli`): stdio, no daemon (ADR-004).
- Only connections with `mcp.exposed = true` are visible; repository ones, only if the
  repository was trusted (`spelunk trust`). `prompt` passwords and unknown SSH hosts are
  rejected (there is no interface).
- Layers implemented in the core (`classify.rs`, `readonly.rs`): a classifier with
  `sqlparser` (including parenthesized `EXPLAIN (ANALYZE)`, DML in CTEs, `SELECT INTO`,
  `FOR UPDATE`, several statements; `TABLE t` is rejected because sqlparser does not
  understand it); in PostgreSQL `BEGIN READ ONLY` + `statement_timeout` + a server-side
  cursor to read only the rows that fit + always `ROLLBACK`; in SQLite a read-only
  connection + `PRAGMA query_only`. Tested that `nextval()` (which the parser lets through)
  is stopped by the transaction (25006).
- Found by a flaky test: if the client timer and `statement_timeout` match, the client
  cancellation can arrive late and cancel the ROLLBACK itself, leaving the session in an
  aborted transaction. Now `statement_timeout` leads and the client waits 2 s more; if it
  still expires, it retries the ROLLBACK until it works.
- Append-only audit log in `state.db` (crate `spelunk-store`, triggers that prevent
  modifying it); `spelunk audit` shows it.
- Responses as Markdown tables, cells of at most 200 characters and about 60 KB per
  response; the server instructions warn that the data is untrusted.
- Pending: profiles (`--profile`), MCP-specific credentials per connection and confirmed
  writes (v0.3).

## Revisit if
Remote agents need access (then Streamable HTTP with authentication).
